# CamBrowser — Ethernet-браузер для JC1060P470C

> Ветка проекта: `feature/ethernet-browser` (базируется на `feature/camos` @ 8ab3d61)
> Железо: ESP32-P4 + JD9165 1024x600 (MIPI-DSI) + тачскрин + **W5500 (SPI-Ethernet)**

## 1. Идея

Подключаем Ethernet-кабель к плате и превращаем её в **сетевой терминал с браузером**:
кабель → DHCP → HTTPS → поиск (Google / DuckDuckGo) → чтение страниц на экране.
Тачскрин работает как клавиатура и навигация, дисплей 1024x600 — как окно браузера.

Формулировка задачи: «подключаем ethernet кабель и открываем браузер, ходим в гугл».

Что получает пользователь на железе:

| Шаг | Что происходит на экране |
|---|---|
| Загрузка | Камера-превью (как раньше), внизу статус сети: `ETH: link... → DHCP...` |
| IP получен | Экран браузера: строка поиска + экранная клавиатура |
| Печать запроса | Тап по клавиатуре, кнопка `GO` |
| Результаты | Список заголовков страниц (до 20), тап — открыть |
| Чтение | Текст страницы с прокруткой `▲▼`, кнопки `HOME / BACK` |

## 2. Железо: как подключить кабель

На плате JC1060P470C **нет Ethernet-PHY** — у ESP32-P4 есть только MAC.
Самый простой и надёжный путь — модуль **W5500** (~$3, «Ethernet module»),
подключается по SPI и поддерживается IDF нативно (`esp_eth`, драйвер w5500):

```
 W5500 module            ESP32-P4 (JC1060P470C)
 ┌─────────────┐
 │ VCC  3.3V   ├────────── 3V3 (НЕ 5V без уровня!)
 │ GND         ├────────── GND
 │ MOSI        ├────────── GPIO11 (Kconfig EB_W5500_MOSI)
 │ MISO        ├────────── GPIO13 (EB_W5500_MISO)
 │ SCLK        ├────────── GPIO12 (EB_W5500_SCLK)
 │ CS/SCSn     ├────────── GPIO10 (EB_W5500_CS)
 │ INT/INTn    ├────────── GPIO9  (EB_W5500_INT; -1 = polling 20 мс)
 │ RSTn        ├────────── GPIO14 (EB_W5500_RST; -1 = не подключён)
 └───┬─────┬───┘
     │RJ45─┴──── Ethernet-кабель → роутер
```

SPI-шина по умолчанию GPSPI2 (`EB_W5500_SPI_HOST=1`; `2` = GPSPI3).
Все пины меняются в menuconfig — **сверить с актуальной схемой платы**, чтобы не
пересечься с периферией (занято: SCCB 7/8, LCD RST 27, подсветка 23, RST тача 5).
При `INT = -1` драйвер W5500 переводится в режим опроса (`poll_period_ms = 20`),
что позволяет работать вообще без провода прерываний.

Альтернатива (не реализована): внутренний EMAC ESP32-P4 + RMII-PHY (IP101/LAN8720
модуль) — быстрее SPI, но требует точной распиновки RMII; оставить на Ф3+.

## 3. Архитектура

```
main/
  main.c                 — точка входа: при CamBrowser камера НЕ инициализируется,
                           сразу backlight + browser_start(); камерный путь целиком
                           под #else (чистый CamOS без изменений)
  app_lcd.c/h            + fb-акцессоры для браузера (app_lcd_get_fb / app_lcd_flush)
  net/
    app_eth.c/h          — W5500 (SPI) → esp_eth → esp_netif → DHCP, статус API
  camos/
    ui.c/h               — примитивы RGB565: rect/text/box (общий шрифт 8x8)
    touch.c/h            — I2C-тач: автопроба GT911 / FT5x06 / CST816 + polling
  browser/
    browser.c/h          — стейт-машина UI: SPLASH → HOME → RESULTS → PAGE (+клавиатура)
    web_client.c/h       — HTTPS GET (esp_http_client + mbedTLS cert bundle)
    html_text.c/h        — парсеры: SERP (результаты) и «страница → текст»
```

Поток данных:

```
[RJ45]──W5500──SPI──▶ esp_eth ──▶ esp_netif/DHCP ──▶ lwip
                                                     │
esp_http_client (mbedTLS, cert bundle) ◀─────────────┘
   │ HTTPS GET (без gzip: Accept-Encoding: identity)
   ▼
PSRAM-буфер (до 384 КБ) ──▶ html_text (strip tags/entities) ──▶ browser.c
   ▼
ui.c ──▶ фреймбуфер DPI (RGB565, PSRAM) ──▶ esp_lcd_panel_draw_bitmap ──▶ JD9165
   ▲
touch.c (I2C polling 30 Гц) ── координаты ── стейт-машина браузера
```

Камера при входе в браузер **останавливается** (`app_video_stream_task_stop`):
её задача больше не перезаписывает фреймбуферы, экран целиком отдаётся UI.
Обратное включение камеры — Ф3 (`app_video_stream_task_restart`).

## 4. Модули: что именно сделано

| Модуль | Ответственность | Ключевые решения |
|---|---|---|
| `net/app_eth` | SPI-шина, W5500 MAC+PHY, netif, DHCP | события `ETHERNET_EVENT_*` и `IP_EVENT_ETH_GOT_IP` → атомарный статус; строка IP для статус-бара |
| `camos/touch` | автопроба тача на своей I2C-шине | GT911 (0x5D/0x14, 16-битные регистры), FT5x06 (0x38), CST816 (0x15); polling 30 Гц без INT; swap/mirror через Kconfig |
| `camos/ui` | рисование на RGB565 | шрифт 8x8 переиспользован из `app_overlay` (таблица сделана внешней); scale 2 (текст 16px) и 3 (заголовки) |
| `browser/web_client` | HTTPS GET | `esp_crt_bundle_attach` (проверка сертификатов ON, без опций «небезопасно»); UA настольного Chrome; редиректы 10; буфер ответа в PSRAM с потолком `EB_MAX_BODY_KB`; `Accept-Encoding: identity` (gzip не декодируем) |
| `browser/html_text` | HTML → данные | DDG html-endpoint (`result__a` + распаковка `uddg=`-редиректа); Google — best-effort по `<h3>`/`<a href>`; срез `<script>/<style>`; entity-декод; фильтр в printable ASCII |
| `browser/browser` | UI | стейт-машина; клавиатура QWERTY-блок + цифры + `[SPC][DEL][GO][DDG/GGL]`; кнопки `▲▼ HOME BACK`; перерисовка только по событию, полный flush фреймбуфера |

## 5. Поисковые машины: честные ограничения

- **DuckDuckGo HTML (`html.duckduckgo.com/html/?q=`)** — по умолчанию: стабильная
  разметка, минимум мусора, не требует cookies. Бот-защита мягче, но при злоупотреблении
  возможны троттлинг/антибот-страницы (детектится по отсутствию `result__a` → сообщение на экране).
- **Google (`www.google.com/search?q=...`)** — опция в menuconfig. Разметка SERP
  меняется без предупреждения; из ДЦ-подсетей возможна captcha; из ЕС — consent-редирект
  (смягчается cookie `CONSENT=YES+...`, зашито в клиент). Парсер best-effort.
- HTML рендерим **только статически**: без JS, без CSS, без gzip, без картинок.
  Латиница/цифры/пунктуация — да; кириллица шрифтом 8x8 не покрыта (план Ф3:
  8x16-шрифт с кириллицей) — сейчас non-ASCII заменяется на `?`.

## 6. Роадмап

### Фаза 0 — Сеть + каркас UI (эта ветка, готово в коде)
`app_eth` (W5500/DHCP), `ui`, `touch` (автопроба), `web_client`, `html_text`,
`browser` (SPLASH/HOME/RESULTS/PAGE + клавиатура), интеграция в `main.c`.
Критерий: в логе видны `eth link up` → `got ip`, на экране — строка поиска,
запрос с тач-клавиатуры возвращает список результатов.

### Фаза 1 — Надёжность на реальной сети
Ретраи и таймауты DNS/TLS, детект антибот-страниц, gzip (mbedtls - inflate),
кириллический шрифт 8x16, авто-переключение DDG→Google при пустом SERP.

### Фаза 2 — Навигация и удобство
История/закладки в NVS, мульти-«вкладка» (стек страниц), ввод URL вручную
(не только поиск), кэш страниц в PSRAM, resume камеры клавишей.

### Фаза 3 — Альтернативные каналы
RMII-PHY на внутреннем EMAC (быстрее), режим «камера-превью + сетевой статус»
одновременно, экспериментально: Wi-Fi через ESP32-C6 (`esp_wifi_remote`) как
fallback, если кабель не подключён.

## 7. Риски и открытые вопросы

- **Пины не сверены со схемой платы** — все пины W5500 и I2C тача выведены в
  menuconfig; перед прошивкой сверить с распиновкой платы/разъёма.
- **Тач-контроллер неизвестен** (наследие CAMOS.md) — автопроба 3 кандидатов
  снимает часть риска; калибровка зеркал — Kconfig-флагами.
- **Google против ботов** — ожидаемо нестабилен; DDG по умолчанию.
- **Память**: TLS-сессия ~40-50 КБ internal heap + буфер тела 384 КБ PSRAM —
  на 32 МБ PSRAM / 768 КБ internal это безопасно, но браузер запускается
  **после** остановки камеры, чтобы не конкурировать за фреймбуферы.
- **Не собрано в этой среде**: код написан под ESP-IDF 5.5/6.0 (API стабильны),
  но в песочнице нет toolchain — проверить `idf.py build` на машине разработчика
  (процедура — docs/BUILD_IDF6.md), затем верифицировать на железе.

## 8. Медиа: радио, видео и SD-карта

Радио и видео идут через `esp_player` (GMF-пайплайн): `io_http` → `extractor` →
декодеры → `aud_render` (ES8311 на I2S0, PA на GPIO11) / видеорендер на RGB-панель.
Файлы также играются с SD-карты (FAT, монтируется в `/sdcard`).

### Ограничение видеодекодера: только H.264 Constrained Baseline

Видеодекодер — программный (`esp_h264`, ядро tinyh264/h264bsd). Он поддерживает
**только профиль Baseline (Constrained Baseline)**. Потоки Main/High отбрасываются
на валидации SPS — в логе это выглядит так:

```
E H264_DEC: profile_idc is error
E H264_DEC: Decode sequence parameter set error.
E H264_DEC.SW: Serious error in decoding, failed to activate param sets
```

Картинки при этом не будет (аудио-дорожка декодируется отдельным трактом).
Проверка профиля своего файла: `ffprobe -show_entries stream=profile` — должно
быть `Constrained Baseline` (или `Baseline`).

Практические следствия:

- большинство публичных тестовых mp4 (test-videos.co.uk, gtv-videos-bucket,
  W3C-сэмплы) закодированы в **High/Main** — для платы не годятся; именно поэтому
  первые пресеты видео не играли;
- в `media/` лежат два перекодированных в Constrained Baseline клипа Big Buck
  Bunny: 360p (lvl 3.0, ~1.2 МБ) и 480p (lvl 3.1, ~1.7 МБ), AAC-LC 44.1 кГц,
  faststart; пресеты видео в `browser.c` ссылаются на них через
  `raw.githubusercontent.com` (Range-запросы поддерживаются);
- перекодирование своих файлов:
  `ffmpeg -i src.mp4 -c:v libx264 -profile:v baseline -level 3.1 -pix_fmt yuv420p -c:a aac -movflags +faststart out.mp4`;
- разумный потолок для плавного софтового декода на P4 — 480p@30; 720p и выше,
  скорее всего, не поспевают по CPU.
