# OV02C10: полная карта возможностей на плате JC1060P470C (ESP32-P4)

> Ветка `ov02c10-full-capability`. Документ отвечает на вопрос:
> **«работаем ли мы с максимальными параметрами камеры или что-то не используем?»**
> и фиксирует, что удалось разблокировать, а что физически недостижимо и почему.

Даташит: OmniVision **OV02C Product Brief v1.1** (Nov 2022), 2 MP, 1/7.25", PureCel Plus-S.
Эталонный открытый драйвер: **Linux kernel mainline** `drivers/media/i2c/ov02c10.c`
(Copyright (c) 2022 Intel Corporation, GPL-2.0) — единственный публичный источник
регистровых настроек, использован для сверки и расширения возможностей.

## 2. Режимы сенсора (таблицы в драйвере)

Все три режима — RAW10, вход MCLK 24 МГц, Bayer **GBRG**:

| # | Режим | MIPI | pclk | HTS | VTS | Теор. fps | Буфер RGB565 | Назначение |
|---|---|---|---|---|---|---|---|---|
| 0 | 1288x728 | 1 lane | 81.67 МГц | 2280 | 1164 | 30.77 | 1.79 MB | Оконный 720p, запас по полосе. **По умолчанию** |
| 1 | 1920x1080 | 1 lane | 81.67 МГц | 2280 | 1164 | 30.77 | 4.15 MB | **Полные 2 MP** — максимум для ESP32-P4 |
| 2 | 1920x1080 | 2 lane | 81.67 МГц | 1140 | 2328 | 30.77 | 4.15 MB | Те же 2 MP, обе линии CSI (проверить разводку!) |

`fps = pclk / (HTS × VTS)` — при замере на железе в режиме 0 получено 30.14 fps
(~2% съедает связка PPA + DSI), что подтверждает расчёт.

Переключение режима: `idf.py menuconfig` →
**Camera Sensors Support → OV02C10 → Default format select**.

Ограничение памяти: режим 1/2 требует 2 × 4.15 MB = 8.3 MB PSRAM под кадровые
буферы (плюс 2.4 MB под LCD) — при 32 MB PSRAM запас большой.

### Почему 1920x1080 — это потолок

Аппаратный предел ISP ESP32-P4 (из `isp_ll.h` IDF 6.0.3):

```c
#define ISP_LL_HSIZE_MAX   1920
#define ISP_LL_VSIZE_MAX   1280
```

Linux-драйвер выводит полный кадр с бордюром **1928x1092** — на ESP32-P4 он
проходить через ISP не будет (1928 > 1920). Поэтому 1920x1080 — фактический
максимум этой связки сенсор+чип, и он теперь доступен одной галочкой.

## 3. Что добавлено в этой ветке

### 3.1 Режим 1920x1080 — готов к использованию

Таблица регистров лежала в драйвере всегда, но приложение показывало от кадра
1080p только верхний левый угол (жёстко зашитый блок 1024x600, offset 0,0).
Теперь геометрия PPA вычисляется динамически по фактическому разрешению (§ 3.4).

### 3.2 Тестовый шаблон — 4 типа (было: только вкл/выкл)

Реестр `0x4503`: бит 7 — включение, биты [1:0] — тип. Совместимо с Linux-драйвером:

| Значение | Тип |
|---|---|
| 0 | Выключен (живое изображение) |
| 1 | Color Bar |
| 2 | Top-Bottom Darker Color Bar |
| 3 | Right-Left Darker Color Bar |
| 4 | Color Bar type 4 |

Применение: `idf.py menuconfig` → **Example Configuration → Camera Sensor Test
Pattern** — или во время выполнения:

```c
struct v4l2_ext_control control = { .id = V4L2_CID_TEST_PATTERN, .value = 1 };
struct v4l2_ext_controls controls = {
    .ctrl_class = V4L2_CTRL_CLASS_USER,
    .count = 1,
    .controls = &control,
};
ioctl(video_fd, VIDIOC_S_EXT_CTRLS, &controls);
```

Шаблон генерируется сенсором и проходит весь тракт (MIPI-CSI → ISP → буфер),
что позволяет проверять конвейер без оптики — полезно при диагностике
«чёрного экрана».

### 3.3 Управление частотой кадров (VBLANK / VTS)

Новое в ветке: контроль `ESP_CAM_SENSOR_VBLANK` в драйвере сенсора +
маппинг на стандартный `V4L2_CID_VBLANK` в esp_video. Семантика V4L2:
`vblank = VTS - height`. Формула:

```
fps = pclk / (HTS × (height + vblank))
```

- нижняя граница = дефолтный VTS режима (быстрее 30 fps нельзя — MIPI-тайминг
  на них рассчитан, это же ограничение выбрано в Linux-драйвере);
- верхняя граница = 0xFFFF (16-битный регистр VTS);
- попутно расширяется максимальная экспозиция: `max_exp = VTS - 15` строк,
  что полезно при слабом освещении;
- кэш `isp_info->vts` синхронизируется, поэтому пересчёт экспозиции
  (макросы `EXPOSURE_V4L2_TO_OV02C10`) и петля AE остаются корректными;
- смена режима сенсора восстанавливает дефолтный VTS.

Приложение применяет override на старте: **Example Configuration → Camera
Frame Rate Override in fps** (0 = дефолт режима). Пример: значение 15 для
режима 0 даёт VTS 1164 → 2388, расчётные 15.07 fps.

### 3.4 Динамическая геометрия PPA (вывод на LCD 1024x600)

Вместо зашитых по платам блоков — расчёт по фактическому кадру, два режима:

**Crop center (по умолчанию)** — блок размера LCD из центра кадра, масштаб 1:1.
Самая резкая картинка; за пределами аспекта LCD кадр обрезается:
- 1288x728 → блок 1024x600 с отступом (132, 64);
- 1920x1080 → блок 1024x600 с отступом (448, 240) — «зум» 1:1.

**Scale to fit (letterbox)** — весь кадр вписывается в LCD с сохранением
пропорций, чёрные полосы где нужно. Гранулярность масштабирования PPA = 1/16:
- 1288x728 → масштаб 0.75 → 966x546;
- 1920x1080 → масштаб 0.5 → 960x540.

Выбор: **Example Configuration → Camera to LCD display fit mode**.
Код работает с любым разрешением сенсора — геометрия считается при первом кадре.

### 3.6 Динамическое определение SCCB-адреса (автосменa при необходимости)

Задача: если модуль камеры отвечает на другом I2C-адресе (другая Sid-перемычка,
ноутбучный модуль, OEM-плата) — найти его автоматически, без правки конфигов.

Как это работает (всё на этапе инициализации `esp_video_init`):

1. Драйвер ov02c10, как и раньше, опрашивается на своём штатном адресе 0x36.
2. Если детект не удался — **сканируется вся I2C-шина** (адреса 0x08–0x77,
   `i2c_master_probe`), все ответившие устройства печатаются в лог
   (`I2C device ACK at address 0x..`) — это одновременно диагностика: пустой
   скан = проблема питания/шлейфа, а не адреса.
3. Детект **повторяется на каждом найденном адресе** (кроме уже опробованного):
   для каждого создаётся SCCB-устройство, вызывается detect драйвера.
   Идентификация по chip ID (0x300a/0x300b = 0x5602) выполняется внутри
   драйвера, поэтому чужие I2C-устройства безопасно пропускаются.
4. При успехе — победивший адрес остаётся рабочим на всю сессию («адрес
   меняется при необходимости»), в логе:
   `MIPI-CSI camera sensor detected at dynamic SCCB address 0x..`.

Дополнительно в драйвере сенсора:

- чтение ID повторяется до 3 раз с паузой 25 мс (медленный ramp питания);
- лог различает «нет ответа» и «отвечает нулями» (второе — типичный признак
  проблем с питанием/тактированием модуля, а не с адресом);
- читается и логируется суб-ревизия 0x300c: модули IPU3-эры и плата
  JC1060P470C дают полный ID 0x5602, ноутбучные модули IPU6-эры — 0x560243
  (2-байтовая проверка PID принимает оба варианта);

## 4. Полный список V4L2-контролов камеры (через `/dev/video0`)

| V4L2 CID | Что делает | Диапазон |
|---|---|---|
| `V4L2_CID_EXPOSURE` / `V4L2_CID_EXPOSURE_ABSOLUTE` | Экспозиция (строки / мкс) | 8 … VTS-15 (мкс пересчитывается) |
| `V4L2_CID_GAIN` | Абсолютный гейн (индекс таблицы) | до 63x (лимит Kconfig 66x) |
| `V4L2_CID_VBLANK` | Вертикальный гейтинг → fps | (VTS_режима - height) … 0xFFFF-height |
| `V4L2_CID_VFLIP` / `V4L2_CID_HFLIP` | Переворот кадра | 0/1 |
| `V4L2_CID_TEST_PATTERN` | Тестовый шаблон | 0-4 |
| `V4L2_CID_CAMERA_GROUP` | Групповая запись экспозиция+гейн | — |
| `V4L2_CID_CAMERA_STATS` | Статистика AE/AWB для esp_ipa | — |

AE/AWB/HIST работают автоматически (esp_ipa + JSON-профиль
`cfg/ov02c10_default.json`); перечисленные CID нужны для ручного/прикладного
управления. AWB по субокнам недоступен на кристаллах rev < 3.0 (ваше v1.3) —
AWB работает по всему кадру, предупреждение в логе безвредно.

## 5. Что НЕ используется и почему (честный список)

### 5.1 60 fps — публично недостижимо

Даташит обещает 2MP@60fps, но ни Linux-драйвер Intel, ни какие-либо другие
открытые проекты таблиц 60 fps не содержат — там ровно один режим
1928x1092@30 (1-lane/2-lane варианты). Регистры PLL/таймингов для 60 fps
доступны только по NDA с OmniVision. Плюс на 1-lane 1080p60 RAW10 требуется
~1.2 Гбит/с полезной нагрузки — потребовалась бы и перенастройка MIPI.

### 5.2 Multi-frame HDR — нет ни таблиц, ни конвейера

Даташит: «multi-frame HDR at 30 fps real time video streaming». Для этого
нужны регистры мультиэкспозиционного считывания и слияние кадров в ISP —
в ESP32-P4 ISP такого блока нет, а регистров сенсора в открытом доступе нет.

### 5.3 Binning 640x480 — нет таблиц

Даташит: «2x2 binning RGB (640x480): 60 fps» — режим интересен для низкой
освещённости, но настроек регистров публично нет.

### 5.4 Linux-режим 1928x1092 — упирается в ISP

Официальный Linux-драйвер выводит 1928x1092 (полная матрица с бордюром).
`ISP_LL_HSIZE_MAX = 1920` делает этот режим невозможным на ESP32-P4.
Использован эквивалент 1920x1080 (режим 1).

### 5.5 Неприменимо к данному приложению

- **Always-On presence** (сенс присутствия пользователя в ультранизком
  потреблении) — фича ноутбуков, в IDF конвейера нет;
- **multi-camera synchronization** — камера одна;
- **2-wire serial output** — альтернатива MIPI, не нужна;
- **SCCB частота** — уже 100 кГц (максимум по спеке 400 кГц можно поднять
  в Kconfig, ускоряет только инициализацию).

## 7. Верификация ветки

Сборки ESP-IDF 6.0.3 (`idf.py set-target esp32p4 && idf.py build`), все — exit 0:

1. Режим по умолчанию 1288x728@30 (1 lane);
2. 1920x1080@30 (1 lane) + Scale-to-fit + Test Pattern 1 + fps override 15;
3. 1920x1080@30 (2 lane).

Проверка на железе (прошивка + визуальная оценка цветов/леттербокса/fps по
логу `fps:`) — за владельцем платы.

## 8. Исследование: OV02C10 в ноутбуках (что удалось выяснить)

Сенсор OV02C10 — массово ноутбучный: он ставится в Dell XPS 13 9340/9350,
XPS 14 9440, XPS 16 9640 (Meteor/Lunar Lake), Samsung Galaxy Book3/4 и другие
платформы Intel IPU3/IPU6 под ACPI HID `OVTI02C1`. Изучены все публичные
источники — итоги:

### 8.1 Архитектуры ноутбуков — три принципиально разные схемы

| Схема | Ноутбуки | Что это значит для переноса модуля на ESP32-P4 |
|---|---|---|
| Прямой I2C + Intel IPU6 | Samsung Galaxy Book3/4 | сенсор на обычной I2C-шине, адрес задаётся BIOS (DSDT) — скан шины (3.6) находит его автоматически |
| Lattice AI USB-мост | Dell XPS 14 9440 / 16 9640 | сенсор за USB-мостом: НЕ является обычным I2C-устройством хоста, управление через Intel CVS (INTC10E0) handshake — подключить такой модуль напрямую к P4 так просто не получится |
| Intel IPU3-эра | ранние ноутбуки с OVTI02C1 | прямой I2C, chip ID 0x5602 — как у нашего модуля |

### 8.2 Практически важные отличия ноутбучных модулей

- **Частота XVCLK**: mainline-драйвер Linux принимает только 19.2 МГц;
  Samsung Galaxy Book3 тактирует сенсор на 26 МГц (патчи сообщества добавляют
  её в белый список). Наша плата JC1060P470C даёт 24 МГц (регистровые таблицы
  в этом драйвере — «24Minput»). При экспериментах с ноутбучным модулем
  без собственного генератора частоту нужно учитывать: PLL-таблицы под 24 МГц
  на 26 МГц дадут завышенный pclk (~8% быстрее).
- **Chip ID/ревизия**: Intel ipu6-drivers проверяет 3-байтовый ID 0x560243
  (IPU6-эра), mainline и ESP-драйвер — 2-байтовый 0x5602 (старшие байты
  совпадают, детект нашего драйвера принимает оба варианта).
- **Питание и управление**: в ноутбуках сенсором управляет INT3472 (дискретный
  контроллер питания/GPIO) или Intel CVS — они подают AVDD/DVDD/DOVDD и
  управляют reset/PWDN. Наша плата питание подаёт сама, reset/PWDN не
  подключены (Kconfig -1) — модуль должен быть самодостаточным по питанию.
- **Драйверы Windows**: пакеты для ноутбуков содержат INF с ACPI\OVTI02C1 и
  бинарники; адрес I2C в них не хранится (он в DSDT BIOS). Для наших целей
  (регистры, адресация, режимы) всё существенное уже есть в открытых
  Linux-драйверах — качать Windows-пакеты не требуется.

### 8.3 Диагностика по логу, если сенсор не находится

Новая логика (3.6) делает источник проблемы видным сразу:

| Что в логе | Что это значит |
|---|---|
| `no I2C device answered the bus scan` | на шине никого: питание модуля, тактирование, шлейф FPC |
| `sensor ACKs but PID=0x0000` + адрес 0x36 | устройство отвечает нулями: типично при живой линии I2C, но проблемных AVDD/DOVDD/XVCLK (например, шлейф сидит криво) |
| `retrying ... at SCCB address 0xNN` → `Detected` | модуль на нештатном адресе — найден автоматически |
| обычный `Detected Camera sensor PID=0x5602` | всё штатно |
